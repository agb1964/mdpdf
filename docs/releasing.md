# Выпуск `mdpdf`

Релизы создаёт `.github/workflows/release.yml`. Публикация запускается только
push тега `v*`; ручной `workflow_dispatch` собирает артефакты, но не создаёт
GitHub Release.

## 1. Подготовка версии

1. Убедиться, что рабочее дерево чистое и ветка `master` синхронизирована с
   `origin/master`.
2. Выбрать версию по Semantic Versioning.
3. Обновить `version` в `Cargo.toml` и синхронизировать `Cargo.lock`.
4. Перенести изменения из раздела `Unreleased` в версионный раздел
   `CHANGELOG.md` с датой выпуска.
5. Обновить `docs/progress.md` и пользовательские разделы `README.md`.
6. Проверить лицензии кода и всех встроенных шрифтов.

## 2. Локальная проверка

```bash
make ci
git diff --check
```

Если менялись parser, AST validation или escaping:

```bash
make fuzz FUZZ_TIME=300
```

Если ожидаемо изменился результат:

```bash
make golden-update
git diff -- tests/fixtures
```

Golden-файлы не обновляются только ради получения зелёного теста. Перед
выпуском нужно вручную открыть PDF для русского текста, таблицы, вложенных
списков, кода, изображений, оглавления, нумерации заголовков и диаграмм
Mermaid.

## 3. Проверка ветки

1. Закоммитить и отправить подготовку релиза.
2. Дождаться успешного CI на `master`.
3. Проверить jobs Ubuntu, macOS, Windows, `cargo-deny`, coverage,
   `эталонные PDF`, `release binary size` и `работает без Typst в системе`.
4. Скачать CI-артефакт с эталонными PDF и выполнить визуальную проверку.

## 4. Тег и публикация

Версия читается из поля `package.version` в `Cargo.toml`. После того как
изменение версии закоммичено, отправлено в `origin/master` и CI прошёл:

```bash
make release-tag
```

Команда проверяет чистое рабочее дерево, ветку `master`, совпадение HEAD с
`origin/master`, отсутствие такого тега на сервере, затем создаёт
аннотированный тег `vX.Y.Z` и отправляет его в `origin`. Если push оборвался
после локального создания тега, повторный запуск безопасно отправит тот же тег.

После push нужно дождаться успешного workflow `Release`. Он должен создать:

- `mdpdf-aarch64-apple-darwin.tar.gz`;
- `mdpdf-x86_64-apple-darwin.tar.gz`;
- `mdpdf-x86_64-unknown-linux-gnu.tar.gz`;
- `mdpdf-aarch64-unknown-linux-gnu.tar.gz`;
- `mdpdf-x86_64-pc-windows-msvc.zip`;
- лицензии проекта и встроенных шрифтов.

Не следует считать обычный зелёный CI доказательством публикации: release job
отдельно ограничен ссылкой на тег `v*`.

## 5. Smoke test артефактов

Для каждой основной платформы нужно:

1. скачать и распаковать релизный архив;
2. выполнить `mdpdf --version`;
3. преобразовать небольшой Markdown с кириллицей, кодом, emoji и диаграммой
   Mermaid;
4. повторить запуск без `--overwrite` и убедиться, что существующий PDF не
   заменён;
5. открыть PDF и проверить текст, моноширинный код, emoji и диаграмму;
6. убедиться, что установленный Typst не требуется.

Если ошибка найдена после публикации, тег и артефакты не подменяются молча:
готовится исправление и новая patch-версия.

## 6. После выпуска

- проверить страницу GitHub Release и список файлов;
- проверить ссылки на release из `README.md`;
- создать новый пустой раздел `Unreleased` в `CHANGELOG.md`;
- зафиксировать результат и оставшийся долг в `docs/progress.md`.

Версия `1.0` объявляется только после выполнения всех условий ТЗ §24.
