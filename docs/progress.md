## Milestone 3 — Typst → PDF

Сделано:

- `MdpdfWorld`: ограниченное окружение Typst (§32). Отдаёт только `/main.typ`,
  встроенные шрифты и заранее зарегистрированные изображения. Нет доступа
  к файловой системе, окружению, сети, пакетам, системным шрифтам; `today`
  всегда `none`, поэтому вывод не зависит от времени.
- Встроенные шрифты разбираются один раз на процесс через `OnceLock`,
  порядок регистрации фиксирован, покрытие кириллицы проверяется тестом (§34).
- Разрешение изображений (§33): путь канонизируется, принадлежность каталогу
  документа проверяется после раскрытия `..` и симлинков, абсолютные пути
  запрещены, формат определяется по содержимому (PNG/JPEG/GIF/SVG), действуют
  лимиты §40.
- Диагностики Typst переводятся в собственную модель (§37): наружу уходит
  только текст, позиция в сгенерированном Typst и подсказки — без `FileId`,
  Rust-типов и debug dump.
- `EmbeddedTypstCompiler` + трейт `PdfCompiler` по §31; проверка сигнатуры
  `%PDF-` и минимального размера (§39).
- Предупреждения Typst не теряются: печатаются в stderr, PDF всё равно
  создаётся (§38).
- `--check` проходит весь конвейер до компиляции и возвращает 0, не записывая PDF.

Найдено и исправлено при первом же прогоне компилятора:

- изображение выводилось блочной `figure` внутри `par()` — Typst выдавал
  предупреждение «block may not occur inside of a paragraph and was ignored»,
  картинка молча пропадала. Теперь `box(image(...))`, alt уходит строкой
  в PDF как описание, а не как подпись;
- нарушение политики доступа к ресурсу возвращало код 7 вместо 9 (§43);
- диагностики Typst не показывались: пользователь видел только
  «PDF compilation failed» без причины.

## Milestone 4 — интеграция CLI

Сделано:

- Атомарная запись (§6.4): PDF формируется в памяти, пишется во временный файл
  в каталоге назначения, `flush` + `sync_all`, затем переименование. При любой
  ошибке временный файл удаляется, существующий PDF не страдает.
- Защита от молчаливой перезаписи (§6.2): без `--overwrite` — код 8 и нетронутый
  старый файл.
- Сообщения `Created output.pdf` и `Checked input.md`, подавляемые `--quiet`.
- Ошибки валидации AST получили собственный код 5 и позицию в исходнике
  (найдено внешним review, было 4 без позиции).
- `tests/end_to_end.rs` переписан под happy path: 14 сценариев вместо проверок
  «PDF ещё не готов».

Windows-оговорка: `rename` поверх существующего файла там возвращает ошибку,
поэтому старый PDF сначала уводится в резервную копию рядом с целью. Если
второе переименование сорвётся, копия возвращается на место — прежний результат
не теряется. На Unix замена атомарна и резервная копия не создаётся.

Имя выходного файла резервируется атомарно через `File::create_new`: проверка
`exists()` с последующей записью допускала гонку, в которой два параллельных
запуска оба считали файл отсутствующим и второй молча затирал первый.

|---|---|
| Паника на не-ASCII адресе | `source[..scheme.len()]` резал UTF-8 не по границе символа; `![a](dat€:x)` ронял процесс |
| Переполнение стека | `MAX_NESTING_DEPTH` был объявлен, но не применялся: 5000 вложенных цитат → abort, а не ошибка |

алфавит не содержал нужных комбинаций.

## Принятые решения

| Решение | Причина |
|---|---|
| Имя крейта `mdpdf`, каталог остаётся `md2pdf` | Совпадение с командами и примерами ТЗ |
| `typst`/`typst-pdf` подключены уже на Milestone 0 | ТЗ §60 требует закреплённых версий в каркасе |
| `Vec<Spanned<Block>>` вместо `Vec<Block>` | §11 требует диапазоны и разрешает обёртку; структуры узлов §10 остались дословными |
| Проверка границ span — в парсере, не в `validate_document` | Сигнатура валидатора закреплена ТЗ и не принимает исходный текст |
| Добавлен `src/lib.rs`, которого нет в §7 | §42 требует `mdpdf::run_cli()`, то есть библиотечный таргет |
| YAML front matter молча отбрасывается | Решение пользователя; §9 оставлял вопрос открытым, §10.2 запрещает извлекать значения |
| Ошибки печатаются без префикса `mdpdf:` | Формат сообщения задан §16 дословно |
| Шрифты в обычном Git, без LFS | 3 МБ неизменяемых файлов; LFS ломает сборку при checkout без `lfs: true` |
| Лицензия MIT OR Apache-2.0 | Стандарт экосистемы Rust; ТЗ конкретную не задаёт |
| 7 advisories из дерева typst внесены в `ignore` | Безопасных версий нет, а typst закреплён `=0.15.1` (§36) |
| `--emit-ast`/`--emit-typst` без `--output` завершают конвейер успехом | §5.5 прямо говорит это про `--emit-typst`; на `--emit-ast` правило распространено по аналогии |
| Добавлена зависимость `typst-layout` | `PagedDocument` живёт в ней и из `typst` наружу не реэкспортируется |
| Изображение — inline `box`, а не блочная `figure` | В Markdown изображение внутри абзаца; блок внутри `par()` Typst игнорирует |
| Шаблон встраивается в `/main.typ`, отдельного `/template.typ` нет | §21 требует `include_str!`, §32 делает отдельный виртуальный файл необязательным |
| Лимиты структуры документа живут в `ast::limits` | Соблюдать их обязан парсер, а зависеть от слоя `compiler` ему нельзя |
| Недопустимые `--margin`/`--font-size` дают код 6, а не 2 | Проверки §20.2 заданы в главе про генератор и живут в `RenderOptions::validate`; внешний review предлагал код 2 — решение осознанное и закреплено тестами |
| Источник истины `MAX_URL_BYTES` — `typst_gen` | `compiler` уже зависит от `typst_gen` (§31), обратной зависимости быть не должно |

Открытая неоднозначность ТЗ: §42 приводит конвейер, в котором `--emit-*` не
прерывают работу и PDF всё равно пишется по пути по умолчанию, а §5.5 говорит
обратное. Выбран вариант §5.5. Если нужен вариант §42 — менять `AppConfig::from_cli`
(поле `emit_only`) и ранний выход в `app::run`; поведение закреплено тестом
`emit_ast_writes_valid_json_and_succeeds`.

## Недоделки: что, почему и чего будет стоить

Единый список всего незавершённого. Для каждого пункта — в чём он состоит,
почему не сделан и какой риск несёт. Пункты, которые выглядят как недоделка,
но таковой не являются, вынесены в конец раздела.

### 1. Perceptual comparison рендера страницы (§49)

**Что.** §49 перечисляет допустимые проверки эталонных PDF и последней называет
«рендер первой страницы в тестовом окружении и perceptual comparison». Сделаны
все остальные: число страниц, размеры, встроенные шрифты, число изображений.
Попиксельного сравнения нет.

**Почему.** Нужен растеризатор PDF, которого нет в виде Rust-крейта: `poppler`,
`mutool` или `pdfium` — системные зависимости, их пришлось бы ставить в CI-образ.
Плюс библиотека perceptual diff и эталонные PNG. Отдельная сложность — порог
допуска: хинтинг и антиалиасинг отличаются между версиями системных библиотек,
поэтому точное совпадение недостижимо, а «разумный порог» подбирается опытом.

**Риск.** Средний. Структурные проверки ловят пропажу шрифта или изображения
(что уже доказано — так нашёлся баг с моноширинным шрифтом), но не поймают
разъехавшуюся вёрстку: наложение текста, обрезанную таблицу, слипшиеся отступы.

**Оценка.** День работы плюс решение, какой растеризатор тащить в CI.

### 2. `opt-level` и `panic = "abort"` не выбраны (§56, §57)

**Что.** В `[profile.release]` стоят `lto = "thin"`, `codegen-units = 1`,
`strip = true`. `opt-level = "z"` и `panic = "abort"` не включены.

**Почему.** §57 прямо запрещает включать `opt-level = "z"` автоматически:
«он может ухудшить скорость Typst-компиляции. Решение принимается по benchmark».
Benchmark сравнения профилей не проводился, поэтому включать было бы гаданием.
`panic = "abort"` §56 разрешает «только после подтверждения отсутствия
негативного влияния на diagnostics» — такой проверки тоже не было.

**Риск.** Низкий. Сейчас 34 МБ и 0.21 с на документ в 1 MiB — оба показателя
приемлемы, выигрыш от подбора профиля скорее косметический.

**Оценка.** Полдня: собрать три-четыре варианта профиля, замерить размер и
время компиляции на наборе документов, записать решение в журнал.

### 3. Память на больших документах (§58)

**Что.** §58 задаёт цель «память для обычного документа до 10 MiB: менее
512 MiB». Факт: документ 10 MiB требует **2.3 ГБ**, вчетверо с половиной больше.
При разрешённом §40 входе в 32 MiB потребление уйдёт в район 7 ГБ.

**Почему.** Память держат не наши структуры — исходник, AST, Typst-строка и
байты PDF вместе дают десятки мегабайт. Остальное занимает вёрстка Typst,
которая строит все страницы в памяти и не умеет работать потоково. Починить
это внутри `mdpdf`, не меняя typst, нельзя.

**Риск.** Средний для больших документов, нулевой для обычных. §58 называет эти
цифры целями, а не требованиями, но пользователь с книгой на 30 MiB получит
отказ по памяти вместо PDF.

**Оценка.** Своими силами — только смягчение: понизить лимит входа §40 либо
предупреждать при документах свыше нескольких мегабайт. Настоящее решение
лежит в typst и от нас не зависит.

### 4. Остаточное TOCTOU-окно при чтении изображений

**Что.** `resolve_resources` канонизирует путь, проверяет принадлежность
каталогу документа, затем открывает файл. Между `canonicalize` и `open`
остаётся окно, в котором путь можно подменить симлинком.

**Почему.** Закрывается только platform-specific средствами: `O_NOFOLLOW`,
`openat2(RESOLVE_NO_SYMLINKS)` на Linux, аналоги на других системах.
Кроссплатформенного способа в стандартной библиотеке нет, а `#![forbid(unsafe_code)]`
и требование пяти платформ §4 делают такую ветку заметной работой.

**Риск.** Низкий при заявленной модели угроз: это однопользовательская CLI,
атакующий должен иметь запись в каталог документа ровно в момент сборки —
то есть уже иметь доступ к исходнику. Ущерб ограничен лимитами §40.

**Оценка.** День на платформенный слой и тесты гонок.

### 5. CI и поставка не проверены в бою

**Что.** У репозитория нет remote. Ни `ci.yml`, ни `release.yml` ни разу
не запускались на GitHub. Всё, что сказано про «зелёный CI», относится только
к локальному `make ci` на macOS ARM64.

**Почему.** Проект не выложен.

**Риск.** **Высокий среди оставшихся.** Непроверенными остаются: сборка под
Windows и Linux (а атомарная запись §6.4 содержит платформенную ветку именно
для Windows), матрица пяти платформ §4, job покрытия, job чистого окружения
без Typst, выкладка артефактов, релиз по тегу. Ошибка в YAML или в шаге
сборки обнаружится только при первом реальном запуске.

**Оценка.** Час на выкладку и первый прогон плюс непредсказуемое время на
починку того, что вскроется.

### 6. Гейт покрытия считает общий процент

**Что.** §17 и §29 требуют не менее 90 % строк по модулям `markdown`, `ast`
и `typst_gen`. CI роняет сборку по общему проценту всего проекта.

**Почему.** `cargo-llvm-cov` помодульного порога не поддерживает. Свой разбор
вывода — это парсинг таблицы, который сломается при смене формата.

**Риск.** Низкий: сейчас все три модуля с большим запасом выше порога, а общий
процент их падение почти наверняка утянет за собой. Но теоретически модуль
может просесть, пока общий процент держится за счёт остальных.

**Оценка.** Полдня, если писать разбор вывода `--json` и падать по модулям.

### 7. Долги по зависимостям

- `ignore` в `deny.toml` — семь advisories из дерева typst, у которых нет
  безопасных версий. Подавление временное, пересматривать при каждом подъёме
  версии typst (§36).
- Дубликат `syn` v2/v3 в дереве оставлен видимым намеренно: он приходит от
  наших прямых зависимостей и исчезнет при обновлении `clap`/`thiserror`.
  Скрывать его через `bans.skip` значило бы потерять сигнал.

### Не недоделки, хотя выглядят похоже

- **`text_content` не используется генератором.** Пользовательский текст всюду
  передаётся строковыми литералами — это более безопасная форма. Функция
  существует и покрыта тестами, потому что §23 требует наличия всех четырёх
  контекстных функций экранирования.
- **Неиспользуемые варианты `TypstGenerationError` и `MarkdownError`.** Оба
  перечисления заданы в §16 и §27 дословно. Удалять варианты, которые пока
  не порождаются, значило бы отступить от ТЗ.
- **Подсветка синтаксиса в блоках кода.** §24.7 прямо запрещает её в первой
  версии: «не выполнять syntax highlighting; язык выводить как небольшую
  подпись». Шаблон делает ровно это.

## Milestone 5 — hardening

Сделано:

- Лимиты §40 применяются на деле: глубина вложенности и число узлов AST
  проверяются в builder-е, размер входа — до чтения в память.
- Три fuzz-таргета §50 (`fuzz_markdown_parser`, `fuzz_typst_escape`,
  `fuzz_ast_validation`) в изолированном крейте `fuzz/`, nightly пинится
  только там. Прогон по 60 с на таргет: падений нет, корпус 4619 / 454 / 4651
  входов. `fuzz_typst_escape` проверяет не только отсутствие паники, но и
  инвариант §22 — из строкового литерала нельзя вырваться.
- `builder` стал `pub(crate)`, тесты инвариантов перенесены внутрь модуля:
  типы `pulldown-cmark` больше не достижимы снаружи крейта (§15).
- `check_spans_within_source` обходит заголовки, абзацы, ячейки таблиц и
  вложенные ссылки с изображениями.
- Предупреждения Typst не теряются на пути ошибки компиляции (§38).
- Ресурс открывается один раз, метаданные и чтение — через один дескриптор.
  Тест на симлинк за пределы каталога документа.
- SVG со ссылками на http/https/file/data отклоняются до вызова Typst (§33.3).
- `path_literal` требует префикс `/mdpdf-resources/`.

Замеры производительности (§58), release-сборка, Apple Silicon:

| Показатель | Цель §58 | Факт |
|---|---|---|
| Запуск без документа | < 100 мс | ~0 мс |
| Markdown 1 MiB, полный конвейер | < 2 с | 0.21 с |
| Пиковая память, документ 1 MiB | — | 250 МБ |
| Пиковая память, документ 10 MiB | < 512 МБ | **2.3 ГБ** |

По времени запас большой, по памяти цель не выполняется: 10 MiB Markdown
(3690 страниц) требует 2.3 ГБ, в 4.5 раза больше заявленного. При разрешённом
§40 входе в 32 MiB потребление уйдёт в район 7 ГБ. Наши структуры — исходник,
AST, Typst-строка, байты PDF — это десятки мегабайт; остальное держит вёрстка
Typst, которая не умеет работать потоково. §58 называет эти цифры целями,
а не требованиями, но расхождение стоит иметь в виду при работе с большими
документами.

- Golden PDF по §49: из каждого PDF извлекаются число страниц, размеры,
  встроенные шрифты и число изображений; эталоны в
  `tests/fixtures/expected_pdf/`. Побайтовое сравнение §49 прямо называет
  непригодным критерием. В CI собранные PDF выкладываются артефактом.
  `lopdf` — только в `dev-dependencies`.

Golden PDF при первом же прогоне нашли дефект, живший с Milestone 2: элемент
Typst `raw` ставит шрифт собственным show-правилом, поэтому обёртка
`text(font: mono-font, ..)` не работала — весь код печатался основным
пропорциональным шрифтом, а `NotoSansMono-Regular` в PDF не попадал вовсе.
Прежние тесты проверяли, что PDF собирается, но не то, что внутри.
