## 2. Назначение программы

`mdpdf` — автономная консольная утилита для преобразования Markdown-документов в PDF.

Основной конвейер:

```text
Markdown
    ↓
собственный AST
    ↓
Typst source
    ↓
встроенный Typst compiler
    ↓
PDF
```

Пользователь получает один исполняемый файл.

**Роль продукта.** `mdpdf` — средство **предварительного** просмотра и
локальной сборки PDF: один бинарник, offline, без зоопарка runtime. Это
**не** эталонный издательский конвейер и **не** требование побайтного
паритета с GitHub, mermaid-cli, pandoc+LaTeX или типографской полиграфией.
Для финальной вёрстки и «как в браузере» допускаются (и часто уместны)
другие инструменты. Нормативное описание Mermaid — §10.5; пользовательская
формулировка — `README.md`.

Для работы программы не должны требоваться:

- установленный Typst;
- Chromium;
- Pandoc;
- LaTeX;
- системные шрифты;
- внешние шаблоны;
- сетевое соединение;
- дополнительные runtime-компоненты.

## 4. Основные принципы проекта

### 4.1. Приоритеты

Приоритеты проекта в порядке убывания:

1. корректность сформированного PDF;
2. отсутствие потери пользовательских файлов;
3. понятные диагностические сообщения;
4. предсказуемое поведение;
5. безопасность обработки локальных ресурсов;
6. автономность бинарника;
7. приемлемое время выполнения;
8. размер бинарника;
9. минимизация потребления памяти на экстремально больших документах.

Размер бинарника и предельная производительность не должны улучшаться ценой усложнения архитектуры или снижения надёжности.

### 4.2. Практический подход

ТЗ задаёт обязательное внешнее поведение, но не требует сохранять внутренние типы, имена файлов и сигнатуры функций дословно.

Внутреннее устройство может изменяться, если сохраняются:

- границы основных этапов;
- безопасность;
- совместимость CLI;
- корректность результата;
- покрытие критических сценариев тестами.

Не требуется сохранять неиспользуемые варианты ошибок, вспомогательные функции или абстракции только потому, что они существовали в первой редакции ТЗ.

## 5. Обязательная архитектура

Проект должен сохранять три независимых основных этапа.

### 5.1. Этап 1 — Markdown → AST

```text
Markdown source → Document AST
```

Этап отвечает за:

- разбор Markdown;
- нормализацию входа;
- построение собственной модели документа;
- сохранение позиций элементов;
- проверку структуры документа;
- применение структурных ограничений.

Этап не должен:

- генерировать Typst;
- импортировать типы Typst;
- создавать PDF;
- читать изображения;
- обращаться к сети.

### 5.2. Этап 2 — AST → Typst

```text
Document AST → GeneratedTypst
```

Этап отвечает за:

- обход AST;
- генерацию безопасного Typst source;
- экранирование пользовательских данных;
- назначение виртуальных путей изображениям;
- формирование списка необходимых ресурсов;
- применение параметров оформления.

Этап не должен:

- повторно разбирать Markdown;
- читать локальные файлы;
- вызывать Typst compiler;
- обращаться к сети;
- использовать абсолютные пути пользователя в Typst source.

### 5.3. Этап 3 — Typst → PDF

```text
GeneratedTypst + разрешённые ресурсы → PDF bytes
```

Этап отвечает за:

- создание ограниченного Typst World;
- регистрацию встроенных шрифтов;
- загрузку разрешённых локальных изображений;
- компиляцию Typst;
- преобразование результата в PDF;
- преобразование диагностик Typst в пользовательский формат.

Этап не должен:

- разбирать Markdown;
- предоставлять Typst произвольный доступ к файловой системе;
- запускать внешний `typst`;
- загружать Typst-пакеты;
- обращаться к сети.

## 6. Технологические требования

### 6.1. Язык и версия

- язык реализации: Rust;
- edition: Rust 2024;
- собственный код проекта должен использовать `#![forbid(unsafe_code)]`.

### 6.2. Основные библиотеки

Используются:

- `pulldown-cmark` для разбора Markdown;
- `typst` для встроенной компиляции;
- `typst-pdf` для формирования PDF;
- `typst-layout`, если он необходим для доступа к `PagedDocument`;
- `mermaid-rs-renderer` для рендера диаграмм Mermaid в SVG (§10.5),
  только с `default-features = false` (без `cli` / `png`);
- `clap` для CLI;
- `thiserror` для типизированных ошибок.

Версии Typst-зависимостей должны быть совместимыми и закрепляться точно.
`mermaid-rs-renderer` — с crates.io (не git), закрепляется `Cargo.lock`.

Текущая рабочая линия:

```toml
typst = "=0.15.1"
typst-pdf = "=0.15.1"
```

`Cargo.lock` должен храниться в Git.

Обновление Typst выполняется отдельной задачей и не объединяется с несвязанными изменениями.

## 7. Пользовательский интерфейс

### 7.1. Основная команда

```bash
mdpdf input.md
```

По умолчанию создаётся:

```text
input.pdf
```

в каталоге исходного документа.

### 7.2. Явный выходной файл

```bash
mdpdf input.md --output output.pdf
mdpdf input.md -o output.pdf
```

### 7.3. Стандартный ввод

```bash
cat input.md | mdpdf - --output output.pdf
```

При чтении из stdin параметр `--output` обязателен.

### 7.4. Проверка документа

```bash
mdpdf input.md --check
```

Команда должна:

1. прочитать Markdown;
2. построить AST;
3. проверить AST;
4. сгенерировать Typst;
5. выполнить компиляцию;
6. не записывать PDF.

### 7.5. Диагностические режимы

```bash
mdpdf input.md --emit-ast ast.json
mdpdf input.md --emit-typst document.typ
```

Если указан только `--emit-ast` или `--emit-typst` без `--output`, программа должна записать запрошенный промежуточный результат и завершиться без создания PDF.

Это поведение является обязательным и устраняет неоднозначность первоначального ТЗ.

### 7.6. Поддерживаемые параметры

```text
mdpdf [OPTIONS] <INPUT>

Arguments:
  <INPUT>                      Markdown-файл или "-" для stdin

Options:
  -o, --output <FILE>          Выходной PDF
      --title <TEXT>           Заголовок документа
      --author <TEXT>          Автор
      --paper <PAPER>          a4 или letter
      --margin <LENGTH>        Поля страницы
      --font-size <LENGTH>     Размер основного текста
      --toc                    Создать оглавление
      --heading-numbers        Нумеровать заголовки
      --check                  Проверить документ без записи PDF
      --emit-ast <FILE>        Записать AST
      --emit-typst <FILE>      Записать Typst source
      --overwrite              Разрешить замену выходного файла
      --quiet                  Не выводить сообщение об успехе
      --verbose                Расширенная диагностика
  -h, --help                   Справка
  -V, --version                Версия
```

## 9. Требования к AST

AST должен быть собственным типом проекта и не должен содержать типы:

- `pulldown-cmark`;
- Typst;
- PDF;
- HTML.

AST должен представлять семантику документа:

- блоки;
- inline-элементы;
- списки;
- таблицы;
- ссылки;
- изображения;
- код;
- исходные позиции.

Конкретные Rust-типы и структура перечислений не фиксируются настоящим ТЗ дословно.

Разрешается изменять внутреннее представление, если:

- все поддерживаемые элементы Markdown сохраняются;
- исходные позиции доступны для диагностик;
- вложенность представлена без потери данных;
- AST не содержит готовых фрагментов Typst;
- golden-тесты отражают ожидаемую семантику.

### 9.1. Исходные позиции

Диагностически значимые элементы должны сохранять диапазон исходного Markdown.

Диапазон может храниться в байтовых смещениях UTF-8.

Преобразование в строку и столбец выполняется при формировании сообщения пользователю.

### 9.2. Валидация

После построения AST должны проверяться:

- корректность вложенности;
- допустимая глубина;
- допустимое число узлов;
- корректность таблиц;
- отсутствие вложенных ссылок;
- отсутствие вложенных изображений;
- допустимость путей изображений;
- корректность исходных диапазонов.

Валидация может быть частью parser pipeline. Не требуется искусственно разделять её на отдельный публичный API, если это не улучшает код.

## 10. Требования к генерации Typst

### 10.1. Основное правило безопасности

Пользовательский Markdown должен интерпретироваться как данные, а не как Typst-код.

Не допускается исполнение пользовательского текста через:

- `#`;
- Typst expressions;
- imports;
- includes;
- package references;
- math syntax;
- comments;
- raw blocks;
- специально сформированные URL или пути.

### 10.2. Экранирование

Генератор должен использовать экранирование, соответствующее контексту.

Допускается не использовать отдельную функцию, если конкретный контекст безопасно обрабатывается строковым литералом Typst.

Не требуется сохранять неиспользуемые функции экранирования только ради совпадения с первой редакцией ТЗ.

Обязательно должны быть покрыты:

- обычный текст;
- метаданные;
- заголовки;
- URL;
- пути ресурсов;
- кодовые блоки;
- содержимое таблиц;
- alt-текст изображений.

### 10.3. Изображения

В Typst source передаются виртуальные пути:

```text
/mdpdf-resources/000001.png
```

Реальные абсолютные пути не должны попадать в сгенерированный Typst.

Генератор формирует список ресурсов, но не читает файлы.

### 10.4. Детерминированность

При одинаковых:

- Markdown;
- параметрах;
- версии программы;

сгенерированный Typst должен быть одинаковым.

Не допускается включать в результат:

- текущее время;
- случайные значения;
- абсолютные пути;
- текущий каталог;
- платформенные сведения.

### 10.5. Диаграммы Mermaid

#### 10.5.0. Статус: предварительный рендер, не эталон

Встроенный Mermaid обеспечивает **просмотр схемы в PDF без Node.js и
браузера**. Требования к качеству:

- результат **пригоден** для технических документов (читаемые flowchart /
  sequence с кириллицей в типичных случаях);
- побайтовый / pixel-parity с Mermaid.js, mermaid-cli или GitHub **не**
  требуется и **не** является критерием приёмки;
- сложная топология (плотные `Note`/`alt`, перекрёстные входы в subgraph,
  длинные подписи рёбер) может давать артефакты раскладки mmdr; упрощение
  исходника диаграммы — допустимый и рекомендуемый обход, а не дефект
  «неправильного Markdown».

Пост-обработка `Layout` в `mdpdf` (подписи sequence, конфликтующие
подписи рёбер flowchart, рёбра к id subgraph, альбомная страница для
широких схем) улучшает отдельные дефекты mmdr, но **не** превращает
конвейер в эталонный рендерер. Расширение качества до уровня mermaid-cli
**вне** объёма обязательной 1.0, если не принято отдельное решение с
пересмотром ТЗ.

Fenced code block с языком `mermaid` рендерится как диаграмма по конвейеру:

```text
mermaid source
    → mermaid-rs-renderer (native Rust, library API)
    → SVG (байты в памяти)
    → виртуальный ресурс `/mdpdf-resources/mermaid-NNNNNN.svg`
    → Typst `#image` / `mdpdf-image` (как для локальных изображений, §11.3)
    → PDF
```

**Запрещено** для рендера Mermaid:

- JavaScript и встраивание JS-движков (V8, QuickJS, Boa, Deno core и т.п.)
  ради прогона Mermaid.js;
- Chromium, Puppeteer, Playwright, WebDriver, mermaid-cli, Node.js;
- внешние процессы и сеть;
- git-зависимости рендерера (только crates.io, `Cargo.lock`);
- feature `cli` / `png` у `mermaid-rs-renderer`
  (`default-features = false`); растеризация в PNG/resvg для диаграмм
  не используется — в PDF идёт векторный SVG.

В AST диаграмма остаётся обычным `CodeBlock` с языком `mermaid`;
диспетчеризация — на этапе генерации Typst (регистрация in-memory
ресурса и вставка `image`).

#### 10.5.1. Движок

Используется крейт
[`mermaid-rs-renderer`](https://crates.io/crates/mermaid-rs-renderer)
(MIT; CLI-имя `mmdr`). Это **native** реализация парсинга, раскладки и
SVG-вывода, а не обёртка над Mermaid.js. Визуальный результат должен быть
**пригоден** для технических документов (flowchart/sequence, кириллица,
типичные схемы) в смысле §10.5.0; побайтовый паритет с mermaid-cli /
GitHub **не** требуется. Деградация до «схематичных прямых без
layout-движка» как **единственный** путь для поддерживаемых типов
недопустима — используется mmdr, а не рисование узлов вручную.

Версия крейта закрепляется `Cargo.lock`. Подъём major/minor —
отдельная задача: `cargo deny check`, полный test suite, ручная проверка
эталонных Mermaid-фикстур (в т.ч. `tests/fixtures/markdown/mermaid.md`
и репрезентативные документы).

Собственный модуль раскладки примитивами Typst (`mdpdf-diagram` /
исторический `src/mermaid/` layout) **не** является целевым путём §10.5.
Удалён 2026-07-31 вместе с внедрением mmdr; имя `mdpdf-diagram` в шаблоне
переиспользовано под блочную обёртку над `image()`.

#### 10.5.2. Поддерживаемые типы

Поддерживаются типы, которые успешно обрабатывает закреплённая версия
`mermaid-rs-renderer` (на момент выбора зависимости — порядка 20+ типов:
flowchart/graph, sequence, class, state, ER, pie, gantt, journey,
timeline, mindmap, gitGraph, C4, block, architecture и др. — по
документации крейта).

Тип или конструкция, которую mmdr не принимает, **не** роняет сборку
документа: блок рендерится как обычный code block, в stderr —
предупреждение. Коды завершения CLI не меняются.

Официальный каталог Mermaid.js остаётся справочником синтаксиса; отсутствие
типа в mmdr = отсутствие в `mdpdf` до обновления зависимости.

#### 10.5.3. SVG и безопасность

Сгенерированный SVG:

- регистрируется как in-memory ресурс с виртуальным путём
  `/mdpdf-resources/...` (не запись во временный каталог пользователя);
- проходит те же проверки, что и пользовательский SVG (§11.3): формат по
  содержимому, запрет внешних ссылок (`http(s):`, `file:`, `data:`,
  network `href` / `xlink:href`);
- учитывается в лимитах на число и суммарный размер изображений (§15);
- вписывается в ширину текстовой области (`width: 100%` или эквивалент);
  блок диаграммы не обязан быть `breakable` между страницами — допускается
  поведение как у крупных изображений.

Пользовательский текст из mermaid-исходника **не** вставляется в Typst
source как код: он остаётся внутри SVG-байтов, которые Typst трактует как
изображение. Экранирование Typst-литералов (§10.2) к содержимому SVG не
применяется; безопасность — проверкой SVG и песочницей Typst World.

#### 10.5.4. Детерминизм

Требование §10.4 сохраняется: один и тот же Markdown + одни и те же
встроенные ресурсы `mdpdf` → одинаковый Typst source (включая имена
виртуальных SVG) и воспроизводимый PDF на поддерживаемых платформах.

Метрики текста внутри mmdr не должны опираться на **неконтролируемые
системные** шрифты хоста. Допускается:

- фиксированный набор метрик / встроенный font config, поставляемый с
  `mdpdf` или mmdr;
- либо явная конфигурация mmdr, исключающая обход системных fontconfig
  каталогов.

Если mmdr по умолчанию сканирует системные шрифты, интеграция обязана
отключить это или зафиксировать font set так, чтобы CI на Ubuntu / macOS /
Windows давал согласованную геометрию в пределах, приемлемых для golden
PDF (структурные проверки; побайтовый PDF по-прежнему не сравнивается).

**Как это выполнено в 0.3.1.** Отключающего API у mmdr нет: база `fontdb`
лежит в приватном модуле. Поэтому `mdpdf` задаёт `Theme::font_family`
заведомо несуществующим именем (`MEASUREMENT_FAMILY` в
`src/mermaid/render.rs`). Запрос в `fontdb` гарантированно не находит
начертания, и mmdr переходит на встроенную табличную метрику — геометрия
перестаёт зависеть от набора шрифтов хоста. В выходном SVG служебное имя
заменяется на `Noto Sans`, которым текст рисует уже Typst из встроенного
набора (§34). Флаг `fast_text_metrics` включён, но самостоятельного
решения не даёт: он действует только на ASCII.

**Остаточное отклонение.** Вызов `load_system_fonts()` внутри mmdr всё
равно выполняется один раз за процесс. Это чтение каталогов, результат
которого не используется ни для геометрии, ни для отрисовки; запись кеша
шрифта в домашний каталог при этом не происходит, потому что выполняется
только после успешного запроса. Убрать сам вызов можно лишь через
upstream-API. Отклонение зафиксировано осознанно и не влияет на
воспроизводимость вывода.

Запрещены в путях и метаданных диаграмм: абсолютные пути хоста, время,
случайные id, сведения об ОС.

#### 10.5.5. Fallback и ошибки

| Ситуация | Поведение |
|---|---|
| mmdr успешно вернул SVG | `image` в PDF |
| синтаксис/тип не поддержан mmdr, ошибка рендера | code block + warning stderr |
| SVG не проходит security-check | code block + warning (или ошибка ресурса — как для битого user SVG; не panic) |
| превышен лимит размера исходника / SVG | как для прочих лимитов §15 |

Частичный рендер «половины» диаграммы не делается: либо целый SVG, либо
целый code block.

#### 10.5.6. Зависимости и cargo-deny

Политика `deny.toml` (§22):

- `mermaid-rs-renderer` — crates.io, MIT;
- `default-features = false`; features `cli`, `png` — **deny**;
- advisories `ttf-parser` / `fontdb`, общие с Typst, — в `ignore` с причиной;
- крейты headless-браузера и JS-движков — в `bans.deny`;
- `unknown-git = deny` (в т.ч. нельзя подтянуть mmdr с GitHub в обход crates.io).

## 11. Требования к встроенному Typst compiler

### 11.1. Ограниченное окружение

Typst World должен предоставлять только:

- основной Typst source;
- встроенный шаблон;
- встроенные шрифты;
- заранее разрешённые изображения.

Typst не должен получать:

- общий доступ к файловой системе;
- системные шрифты;
- домашний каталог;
- переменные окружения;
- сеть;
- Typst Universe;
- произвольные пакеты;
- текущее время.

### 11.2. Шрифты

В бинарник должны быть встроены шрифты, достаточные для:

- обычного текста;
- жирного текста;
- курсива;
- жирного курсива;
- моноширинного кода;
- кириллицы;
- распространённых emoji, для которых нет глифов в текстовых начертаниях.

Текущий комплект включает пять текстовых начертаний Noto Sans/Noto Sans Mono
и Noto Color Emoji. Если символ отсутствует во всех встроенных шрифтах,
программа должна вывести предупреждение в stderr и продолжить создание PDF.

Noto Color Emoji добавлен после подтверждённого дефекта: emoji молча исчезали
из PDF, а системный fallback запрещён. Другие шрифты без пользовательской
потребности добавлять не требуется.

### 11.3. Изображения

Поддерживаются:

- PNG;
- JPEG;
- GIF;
- безопасный SVG.

Перед передачей Typst изображение должно быть проверено.

Запрещены:

- абсолютные пути;
- выход за каталог документа;
- символьные ссылки за пределы каталога;
- HTTP/HTTPS;
- protocol-relative URL;
- `data:` URI;
- SVG с внешними ссылками;
- `file:` URI;
- слишком большие файлы;
- каталоги вместо файлов.

Формат должен проверяться по содержимому, а не только по расширению.

### 11.4. PDF

После компиляции проверяется:

- отсутствие ошибки Typst;
- ненулевой размер результата;
- сигнатура `%PDF-`;
- успешность PDF-exporter.

Полный повторный парсинг каждого PDF в production-коде не требуется.

## 12. Работа с файлами

### 12.1. Выходной файл

Без `--overwrite` существующий PDF не должен изменяться.

Проверка и резервирование имени должны исключать гонку между параллельными процессами.

### 12.2. Атомарная запись

PDF сначала полностью формируется, затем записывается во временный файл в каталоге назначения.

После успешной записи выполняются:

1. `flush`;
2. `sync_all`, если это поддерживается реализацией;
3. безопасное переименование.

При ошибке:

- временный файл удаляется;
- существующий PDF сохраняется;
- резервная копия восстанавливается, если она использовалась.

Платформенные различия Windows и Unix допускаются.

Главное требование: старый корректный файл не должен быть потерян при неудачной замене.

## 13. Диагностика

Ошибки должны быть понятны без знания внутреннего устройства Typst или Rust.

Пример:

```text
input.md:12:5: unsupported Markdown construct: inline HTML
```

Для ошибки изображения:

```text
input.md:18:1: image "images/schema.png" could not be decoded
```

Пользователю не должны показываться без необходимости:

- `FileId`;
- имена внутренних Rust-типов;
- debug dump Typst;
- необработанный backtrace;
- внутренние виртуальные пути без пояснения.

Предупреждения Typst не должны теряться.

Они выводятся в stderr, но сами по себе не блокируют создание PDF.

Отсутствие глифа во всех встроенных шрифтах также является предупреждением, а
не ошибкой компиляции. Диагностика должна перечислять проблемные символы
детерминированно и не должна подключать системный font fallback.

## 15. Ограничения ресурсов

Ограничения нужны для защиты от случайного или намеренно патологического ввода.

Базовые значения версии `1.0`:

- Markdown: не более 32 MiB;
- глубина вложенности: не более 128;
- AST: не более 1 000 000 узлов;
- изображений: не более 1 000;
- одно изображение: не более 64 MiB;
- общий размер изображений: не более 256 MiB;
- URL: не более 16 KiB;
- исходник одной диаграммы Mermaid: не более 64 KiB;
- SVG одной диаграммы Mermaid (выход mmdr): не более 16 MiB;
- (лимиты собственного layout «узлов/рёбер» сняты вместе с удалением
  legacy-кода 2026-07-31; контрактом §10.5 они не были).

Значения могут быть изменены после практического использования.

Это защитные лимиты, а не обещание, что документ максимального допустимого размера будет обрабатываться с малым потреблением памяти.

## 16. Производительность

### 16.1. Реально измеренные показатели

На Apple Silicon для текущей реализации:

| Сценарий | Наблюдаемый результат |
|---|---:|
| Запуск без документа | около 0 мс по измерению оболочки |
| Markdown 1 MiB без изображений | около 0,21 с |
| Пиковая память для 1 MiB | примерно 250–350 МБ |
| Markdown 10 MiB, около 3690 страниц | около 2,3 ГБ памяти |
| Размер release-бинарника | около 44 МБ |

Эти цифры являются контрольной точкой, а не гарантией для всех систем и всех документов.

Рост относительно исходных 34 МБ объясняется добавлением встроенного
Noto Color Emoji.

### 16.2. Требования версии 1.0

Обязательными являются:

- отсутствие очевидных бесконечных циклов;
- отсутствие неконтролируемого роста памяти в собственных структурах;
- завершение обработки обычных технических документов;
- отсутствие существенного ухудшения относительно текущей реализации без объяснимой причины.

Не устанавливается обязательный лимит памяти для Markdown размером 10 MiB.

Причина: Typst выполняет пакетную вёрстку и хранит страницы в `PagedDocument`. Пиковое потребление памяти определяется прежде всего устройством Typst, а не AST или генератором `mdpdf`.

Для существенного уменьшения этого расхода потребовалась бы замена или глубокая переработка backend, что противоречит назначению проекта.

### 16.3. Определение обычного документа

Для планирования и тестирования обычным считается документ:

- размером до нескольких MiB;
- объёмом до нескольких сотен страниц;
- с умеренным количеством изображений;
- без искусственно созданной экстремальной вложенности.

Документы в несколько тысяч страниц поддерживаются по возможности, но оптимизация таких документов не является приоритетом версии `1.0`.

## 17. Политика оптимизации

### 17.1. Основное правило

Оптимизация выполняется только после измерения и только при наличии практически значимой проблемы.

Не следует начинать оптимизацию, если:

- программа уже выполняет типичный сценарий достаточно быстро;
- выигрыш ожидается на уровне нескольких процентов;
- изменение усложняет код;
- требуется значительное увеличение тестовой инфраструктуры;
- проблема возникает только на искусственном benchmark;
- основная стоимость находится внутри Typst и не контролируется проектом.

### 17.2. Основания для оптимизации

Работа по оптимизации оправдана, если выполняется хотя бы одно условие:

1. реальный пользовательский документ обрабатывается неприемлемо долго;
2. возникает нехватка памяти на обычном документе;
3. новая версия ухудшила измеряемый показатель примерно на 20% или более;
4. размер бинарника существенно вырос из-за добавленного кода или ресурсов;
5. profiler показывает конкретное узкое место в собственном коде;
6. оптимизация одновременно упрощает реализацию.

Порог 20% не является математически строгим, но отделяет практически заметный эффект от косметического.

### 17.3. Что не является обязательной задачей

Для версии `1.0` не требуется:

- подбирать `opt-level = "z"`;
- включать `panic = "abort"`;
- сравнивать несколько вариантов LTO;
- уменьшать бинарник на несколько мегабайт;
- устранять дублирование procedural macro-зависимостей;
- оптимизировать структуры AST без данных profiler;
- разрабатывать потоковую вёрстку поверх Typst;
- проводить отдельный benchmark для каждого изменения;
- добиваться произвольного целевого RSS, недостижимого для Typst.

Текущая release-конфигурация:

```toml
[profile.release]
lto = "thin"
codegen-units = 1
strip = true
```

считается достаточной.

Изменять её без практической причины не требуется.

Размер около 44 МБ считается нормальным для автономного бинарника, включающего:

- удаления встроенных шрифтов;
- перехода к внешнему Typst;
- динамической загрузки ресурсов;
- ухудшения диагностики;
- усложнения сборки.

## 19. Тестирование

### 19.1. Обязательные уровни

Проект должен сохранять:

- unit-тесты;
- parser tests;
- AST golden tests;
- Typst golden tests;
- compiler tests;
- CLI tests;
- end-to-end tests;
- security regression tests;
- структурные golden PDF tests.

### 19.2. Регрессионные сценарии

Обязательно должны сохраняться тесты для ранее найденных дефектов:

- не-ASCII последовательность рядом с URI scheme;
- экстремальная вложенность;
- выход изображения за каталог;
- символьная ссылка за каталог;
- protocol-relative URL;
- SVG с внешними ссылками;
- ошибка второго переименования;
- параллельное резервирование output-файла;
- сохранение старого PDF при ошибке;
- корректный код завершения для AST validation;
- вывод диагностик Typst;
- наличие моноширинного шрифта в PDF;
- наличие изображения в PDF.

### 19.3. Покрытие кода

Покрытие используется как информационный показатель.

Обязательный общий порог 90% отменяется.

Причины:

- процент покрытия сам по себе не гарантирует качество;
- наиболее серьёзные найденные дефекты находились в редких ветках, несмотря на высокое покрытие;
- помодульный контроль требует дополнительной нестабильной инфраструктуры;
- работа ради увеличения числа без добавления полезных сценариев не оправдана.

Снижение покрытия критических модулей должно быть замечено при review, но не обязано автоматически блокировать CI по единственному процентному показателю.

Важнее наличие тестов на:

- границы;
- ошибки;
- многобайтовый ввод;
- отказ файловых операций;
- конкурентный запуск;
- патологическую вложенность;
- безопасность путей.

### 19.4. Fuzzing

Fuzz targets должны оставаться в репозитории:

- Markdown parser;
- Typst escaping;
- AST validation;
- Mermaid: вход mmdr / интеграционный путь SVG
  (`fuzz_mermaid_render`).

Постоянный длительный fuzzing в каждом CI-запуске не требуется.

Fuzzing запускается:

- перед значительным релизом;
- после изменений parser или escaping;
- при исправлении ошибок, связанных с произвольным вводом;
- вручную по необходимости.

### 19.5. PDF regression tests

Обязательны структурные проверки:

- PDF открывается parser-ом тестов;
- число страниц ожидаемо;
- размер страниц ожидаем;
- нужные шрифты встроены;
- нужное число изображений присутствует.

Побайтовое сравнение PDF не используется.

## 20. Визуальное сравнение PDF

Автоматический perceptual comparison не входит в обязательные условия версии `1.0`.

Причины:

- требуется внешний PDF rasterizer;
- появляются системные зависимости CI;
- антиалиасинг и font hinting различаются между платформами;
- настройка допустимого порога требует отдельной работы;
- существующие структурные проверки уже находят значимые дефекты.

Перед релизом достаточно вручную проверить небольшой набор эталонных документов:

1. русский технический текст;
2. таблица;
3. вложенные списки;
4. блоки кода;
5. изображения;
6. оглавление и нумерация заголовков;
7. диаграммы Mermaid.

Perceptual comparison следует добавлять только если в проекте регулярно возникают визуальные регрессии, которые не обнаруживаются текущими тестами.

## 22. Dependency audit

`cargo deny check` должен выполняться локально и в CI.

Известные advisories из дерева Typst (и общих транзитивов вроде
`ttf-parser` / `fontdb`, используемых также `mermaid-rs-renderer`) могут
временно находиться в `ignore`, если:

- исправленной совместимой версии нет;
- причина документирована;
- исключения пересматриваются при обновлении Typst и/или
  `mermaid-rs-renderer`.

Наличие двух версий `syn` не является ошибкой runtime и не требует отдельной работы.

Политика Mermaid (§10.5) закреплена в `deny.toml`:

- запрет git-источников;
- запрет крейтов Chromium/WebDriver/JS-runtime для рендера диаграмм;
- запрет features `cli` / `png` у `mermaid-rs-renderer`;
- допустимые лицензии включают `Unlicense` (транзитив regex-стека mmdr).

- уязвимости отсутствуют;
- бинарник работает;
- обновление не даёт пользовательской пользы.

## 23. Ошибки и паники

Пользовательский ввод не должен приводить к panic.

В production-коде не следует использовать:

- `unwrap()`;
- `expect()`;
- `panic!()`;
- `todo!()`;
- `unimplemented!()`.

Допускаются:

- `unwrap()` и `expect()` в тестах;
- документированный `unreachable!()` для действительно доказанного внутреннего инварианта;
- panic внутри внешней библиотеки, который проект не способен контролировать, если нет разумного обходного решения.

`panic = "abort"` специально включать не требуется.

## 28. Критерий завершённости изменений

Изменение считается завершённым, если:

- решает заявленную задачу;
- не нарушает границы трёх этапов;
- не открывает сетевой доступ;
- не запускает внешние процессы;
- не предоставляет Typst произвольный доступ к файлам;
- имеет тесты на основной сценарий;
- имеет тест ошибки, если ошибка практически возможна;
- проходит форматирование и Clippy;
- не ломает существующие regression tests;
- документация обновлена при изменении CLI;
- отсутствует необоснованное усложнение.

Не требуется увеличивать объём тестов или абстракций без связи с реальным риском.

## 29. Итоговое определение готовности продукта

`mdpdf` считается реализованным продуктом, если команда:

```bash
mdpdf document.md -o document.pdf
```

создаёт корректный PDF и выполняются следующие условия:

- Markdown проходит через собственный AST;
- Typst source генерируется безопасно;
- Typst встроен в бинарник;
- внешние программы не требуются;
- сеть не используется;
- системные шрифты не требуются;
- кириллица работает;
- локальные изображения работают;
- произвольный доступ к файлам заблокирован;
- пользовательский ввод не исполняется как Typst-код;
- существующий PDF защищён от потери;
- ошибки содержат полезную причину;
- основные платформы подтверждены реальным CI;
- обычные документы обрабатываются с приемлемой скоростью.

Проект не обязан быть:

- самым маленьким Markdown-to-PDF конвертером;
- самым быстрым PDF generator;
- пригодным для книг в несколько тысяч страниц при малом объёме памяти;
- универсальной реализацией всего Markdown;
- универсальным frontend для Typst;
- платформой для пользовательских шаблонов;
- заменой Pandoc;
- эталонным рендерером Mermaid (mermaid-cli / GitHub) или заменой
  издательского конвейера.

Его задача — надёжно и автономно преобразовывать обычные Markdown-документы
в **приемлемый** PDF одним бинарным файлом (предварительный просмотр и
локальная сборка, §2).
